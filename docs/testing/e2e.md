# End-to-End Testing

One real browser-driven E2E suite (`frontend/e2e/critical-path.spec.ts`,
Playwright), added because no browser automation existed anywhere in
this project before this - Vitest/React Testing Library's jsdom
coverage is real but never exercises an actual browser, a real
network request, or real HTTP streaming end to end.

## What this actually proves

Run against the real dev stack (real FastAPI backend, real Postgres,
real Next.js dev server - not mocked at any layer):

1. **Registration** - fills the real register form, submits to the
   real `POST /auth/register` + `/auth/login`, and lands on an
   authenticated `/library`.
2. **Library listing** - the real `GET /videos` call returns the
   reassigned video (see below) and the UI renders a real link to it.
3. **Media-token-gated playback** - navigating to the video's workspace
   page triggers the real `GET /videos/{id}/media-token` call, the
   `<video>` element's `src` is asserted to actually contain
   `/stream?token=...` (not a placeholder), and the test waits for
   `HTMLVideoElement.readyState >= 1` and `duration > 0` - meaning the
   browser genuinely fetched and parsed real video bytes over the real
   HTTP connection (the same Range-capable streaming endpoint
   `backend/tests/api/v1/endpoints/test_video_stream_media_token_integration.py`
   verifies at the HTTP level, now exercised from an actual browser).
4. **Login** (a second, independent test with its own fresh browser
   context) - the same real user can log in again with the real
   password they registered with.

## What's a disclosed test fixture, not application mocking

A freshly-registered user has no videos, and this project's real AI
pipeline takes on the order of minutes per video on this hardware
(see `docs/benchmarks/performance.md` - a single real RAG LLM call
alone took 60-210 seconds; full 8-stage processing is considerably
more). Running a real upload through real transcription/
summarization/etc. inside this E2E test would make it impractical to
run routinely.

Instead, the test temporarily reassigns one already-processed real
video (with real transcript/summary/embeddings already generated by
an earlier real pipeline run) to the freshly-registered test user, via
a direct `UPDATE videos SET owner_id = ...` against the real database
- not a mock, not a stub, only which row a foreign key points at. The
original owner is restored and the test user is deleted in
`test.afterAll`, verified to leave no trace (checked manually after
every run while building this). No application code path is bypassed
or faked anywhere in the test itself.

**Explicitly NOT covered by this test**: the upload -> processing
journey (upload a file, wait for the real 8-stage pipeline to finish).
That path has its own real coverage - see
`backend/tests/pipelines/test_video_pipeline_orchestration.py`,
`backend/tests/pipelines/test_failure_recovery_integration.py`, and
`frontend/src/hooks/useUpload.test.tsx` - just not as a single,
multi-minute browser-driven test.

## Running it

Requires the real dev stack up (`ai-video-api`, `ai-video-db`, Redis)
and Docker reachable from wherever the test runs (it shells out to
`docker exec ai-video-db psql ...` for the setup/teardown described
above):

```bash
cd frontend
npx playwright install chromium   # once
npm run test:e2e
```

`playwright.config.ts`'s `webServer` block starts/reuses the real
Next.js dev server on `localhost:3000` automatically.

## Why this isn't wired into CI

`tests.yml`/`ci.yml` run against SQLite/no-backend fixtures
specifically so they never need a real Postgres+Redis+API stack
reachable - this E2E suite needs exactly that, plus Docker itself
reachable from the test runner, which GitHub Actions' hosted runners
don't provide out of the box for this project's stack. Documented
here as a real, run-it-yourself-locally suite rather than silently
absent or (worse) faked into looking like a CI-gated one.
