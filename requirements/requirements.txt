# Fully pinned, machine-generated lock file - every line below (direct
# and transitive) is pinned to an exact version. Generated 2026-10-09
# with pip-tools (pip-compile) from requirements.in, constrained
# (`-c`) against a `pip freeze` of the already-built, already-healthy
# ai-video-api/celery containers at the time - i.e. pip-compile was
# biased toward versions already verified to resolve and run
# correctly together, not re-resolved fresh against "whatever's
# newest on PyPI today" (which is exactly the mechanism that caused
# both incidents below).
#
# Why this file exists: requirements.txt used to list bare package
# names with no version pins (see requirements.in's own history/
# comments for the two real incidents - ragas on 2026-10-07 and
# av/faster-whisper on 2026-10-08 - that an unpinned transitive
# resolution caused). A single reactive pin per incident fixes the
# symptom but not the mechanism: the next `pip install` from an
# unpinned file can still silently resolve a different, newer,
# possibly-incompatible version of ANY of the ~140 packages this
# project's AI/ML stack transitively depends on. This file pins all
# of them, so a fresh build reproduces the exact same closure instead
# of re-resolving it.
#
# To intentionally change a version: edit requirements.in (the
# human-maintained direct-dependency list, same file this used to be)
# and regenerate this file - do not hand-edit the pins below except
# to fix a specific, understood incompatibility (as requirements.in's
# own comments document for av/setuptools).
#

# Dockerfile, so resolution happens in the actual target Python/OS,
# not the host machine):
#   pip install pip-tools
#   pip freeze > current-freeze.txt
#   pip-compile requirements.in -c current-freeze.txt \
#       --output-file=requirements.txt --allow-unsafe
# Review the diff before committing - especially any package whose
# version changed from what was already running, since that means
# the old pin no longer resolves and something upstream moved.
